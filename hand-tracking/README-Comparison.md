# A/B 摄像头识别对照

这是独立的摄像头预览模式，不连接 SDK、不使能机械手。A 使用现有 MediaPipe 与个人结构标定；B 使用独立进程中的 WiLoR-mini，模型版本锁在 `wilor-backend/pyproject.toml` 和 `uv.lock`。Windows Python 仍全部由 uv 管理，A 为 3.11，B 为 3.10；不修改 wslc 镜像。

## 启动与停止

双击根目录 `Start-HandCompare.cmd`，打开 <http://127.0.0.1:8090/>。已有普通摄像头预览会先正常退出并释放摄像头；已有 SDK 会话时会拒绝启动，请先停止 SDK 会话。重复启动复用现有对照服务。停止用 `Stop-HandCompare.cmd`，同时关闭预览和独立推理后端。

首次安装需要下载 CUDA PyTorch 和约 2.56 GB 的模型权重，以及检测器与 MANO 文件。后台就绪状态和加载错误会显示在页面。后端仅监听 `127.0.0.1:8093`；页面继续使用 8090。

CUDA PyTorch 使用官方 wheel 的本地副本，由 uv 的路径来源锁定版本；缺失时启动脚本调用分段下载工具，校验锁定 SHA256 后再安装。四个模型文件也已按官方 LFS SHA256 校验。大文件下载工具为 `wilor-backend/download_models.py`，可显式传 `--proxy http://127.0.0.1:8889`，加 `--torch` 下载 CUDA wheel，否则下载模型。分段文件允许中断后续传。CDN 的 Xet ETag 不等于文件 SHA256，校验使用官方 LFS oid。

```powershell
& D:\Dev\wslc\Start-HandCompare.ps1 -NoBrowser
& D:\Dev\wslc\Stop-HandCompare.ps1
```

默认使用 CUDA GPU；没有 CUDA 时明确报错，不自动降为慢速 CPU 推理。调试日志在 `wilor-backend/logs/`。依赖和模型下载可以在启动进程中临时设置 `HTTP_PROXY` / `HTTPS_PROXY`；不需要更改系统代理或现有 A 环境。

## 页面上的三种结果

- 摄像头画面叠加的仍是 MediaPipe 骨架。
- 对照区的两个人手三维骨架来自同一个源帧；按各自掌长归一化，拖动可旋转。它们显示模型原始关键点，不是机械手。
- 后端下拉框控制现有机械手 URDF 预览、角度表及标定面板。A 和 B 经过相同的机器人映射实现；选中 B 不产生 SDK 命令。

B 收到的是同源画面的高质量 JPEG，A 直接读取原帧；这包含轻微编码差异。WiLoR 推理独立运行，最多保留一个待处理新帧。旧帧被覆盖而不排队，页面显示覆盖计数。A 保持原有实时路径，对照区只显示 B 已处理完的配对源帧，因此机械手实时 A 预览可能比配对骨架更新。

指标分别显示 A/B 推理和映射耗时、B 采集到目标的总耗时、当前结果年龄和最近最多 120 帧总耗时 P95。不把模型残差或低抖动当作真实角度精度。若 B 超过现有 200 ms 有效性阈值，预览可拒绝过期目标，原始骨架仍用于观察；不会为试验放宽实机保护。

若页面显示“数据中断”，新版会在连接连续 2 秒无消息时重连；“恢复 / 重新捕获”也会重建异常连接。2026-10-19 已修复骨架旋转事件递归导致页面无法更新的问题，旧标签页需 Ctrl+F5。丢手导致的“已暂停”仍需手动恢复，不自动开始实机运动。开发回归：`node tests/frontend-recovery.cjs`。

WiLoR 检测类别只用来选择左右手，其适配器中的占位分数不是关节精度。若实际左手在 B 显示 Right，选中 B 后切换“左右手校正”；只改变 B 的设置，再点击“恢复 / 重新捕获”。

若 B 标定是在左右手校正开启时采集，下次启动加 `-SwapWiLoR` 保持相同上下文；改变上下文会停用不匹配的配置。

## 独立个人标定

A 使用 `hand-tracking/profiles/current.json`，B 使用 `wilor-current.json`，保存时各自备份。B 配置绑定摄像头、左右手校正和 `tracker=wilor`；不会直接套用 A 的偏置或拇指变换。

WiLoR 标定只需三个静态姿态，每步准备 1 秒、采样 7 秒，至少 20 个有效三维帧：

1. **四指并拢伸直**：掌心朝前，校正四指侧摆零位并记录个人掌面和骨段比例。
2. **四指微张**：手腕保持不动，四指舒适分开约 5–15°，估算个人侧摆比例；不需要张到极限。
3. **拇指向外**：四指并拢，拇指沿掌面向外并略抬起，记录个人拇指方向，并对齐到 URDF 的舒适参考姿态。

该流程保留 WiLoR 的 MANO 三维关节连续解算。并拢和微张样本校正侧摆零位与幅度；拇指样本提供静态方向旋转参考，不做拇指接触约束，也不要求握拳或拇指碰四指。页面隐藏旧的八组拇指专项采样，以免误用。只有三个姿态都通过且点击“应用并保存”后，才会写入 schema 5 配置；旧 WiLoR 配置会留在带时间戳的备份文件中。A 标定不受影响。

A 保留原有八姿态、1 秒准备加 3 秒采样流程。当前 10 秒动态一致性按钮只统计 A，在 B 视图中停用。

## 可选录像和回放

默认不录制。点击“录制 15 秒测试视频”后，将未叠加骨架的摄像头图像保存为本机 `hand-tracking/logs/comparison-时间戳.avi`，可以提前结束。视频可能包含背景和人脸，分享代码时不附带 logs。相机实际帧率不足 15 时录像回放速度可能与真实动作不同，录像主要用于同一输入的识别对照，不用于测量操作者响应延迟。

动作建议：自然伸直、缓慢握拳、钩手、四指张并、连续对指、保持手形小幅转掌。停止当前对照后，指定录像路径重新启动：

```powershell
& D:\Dev\wslc\Start-HandCompare.ps1 -Video D:\Dev\wslc\hand-tracking\logs\comparison-实际时间戳.avi
```

回放代替摄像头输入，以视频标称帧率播放；B 仍采用最新帧策略。逐项结果仅比较显示为相同配对帧编号的骨架。回放结束保留画面，停止脚本退出服务。

## 使用范围

候选模型更像完整人手不代表实际角度必然更准确；人手识别、机器人映射及设备执行误差须分别评估。此对照模式不进入实机控制路径；B 的独立实机模式已接入，使用根目录 `Start-HandFollow.cmd`，详见 [实机说明](README-Full-Follow.md)。切换模式会停止旧摄像头会话，始终需手动开始运动。

来源：[WiLoR 官方](https://github.com/rolpotamias/WiLoR)、[WiLoR-mini](https://github.com/warmshao/WiLoR-mini)。WiLoR 模型采用非商业许可，MANO 和 Ultralytics 另有许可要求，后续产品化须核对各自条款。

## WiLoR + D435 侧摆预览

在项目目录的 PowerShell 中运行以下命令启动独立预览：

```powershell
.\Start-HandMapping.ps1 -Tracker wilor-d435 -NoBrowser
```

它用 D435 同一帧的 RGB、对齐深度和内参，MediaPipe 与 WiLoR 同帧识别。WiLoR 仍决定四指屈伸和拇指；深度与 MediaPipe 只对四指 MCP 侧摆作有置信度门控的弱修正。掌部深度不足或与 WiLoR 先验明显冲突时，该帧沿用 WiLoR。WiLoR 短暂漏检时，MediaPipe 会补上该帧，连续三帧重新识别后才切回 WiLoR；这类补帧不写入 WiLoR 标定。预览模式在手重新出现时会从自动丢手暂停中恢复；页面手动暂停仍需手动恢复。以上直接启动命令只做预览，不连接机械手。实机使用根目录 `Start-HandFollow.ps1 -Tracker wilor-d435`，详见 [全手跟随](README-Full-Follow.md)。独立预览需先运行 WiLoR 后端（8093），用以下命令停止并释放 D435：

```powershell
.\Stop-HandMapping.ps1
```

页面“人手结构”行会显示修正了哪些手指，以及深度质量不足时的回退原因。当前已接受的 WiLoR 三姿态偏置会继续使用；D435 原始观测用于增量修正，不会覆盖标定配置。先以掌心朝向摄像头做张合和四指张并对照，尤其检查侧摆方向与是否有跳变，再决定是否调整融合权重。

该预览对两类短暂中断作去抖：两个模型都没有可用目标时，最多保持上一有效目标 300 ms，保持帧不计入标定或动态验证的有效样本；单手已锁定为 Left 后，腕部位置连续且最近 750 ms 内有真实 Left 确认时，容忍短暂 Right 标签。标签容忍不会自行无限续期，三维解算仍使用模型输出自身的坐标手性。首次捕获、出现多手和标定采样时仍严格选择 Left。页面会分别显示“保持上一有效目标”和“左右标签短暂变化”；持续显示 Right 时应检查实际手和左右手校正设置。

2026-10-20 短暂丢手排查：D435 采集约 30 FPS，但同帧 MediaPipe + WiLoR 串行处理约 8–9 FPS，常见整帧耗时 120–150 ms。原先界面把相机帧率当成处理帧率，而且在两次处理结果之间数据年龄超过 200 ms 时就进入 HOLD。该纯预览模式改为 400 ms 连续性容差；新输入本身超过 200 ms 仍被拒绝，实机及其他模式继续使用原有时限。MediaPipe 补位的左右手分类门槛统一为 0.45，修复检测端允许 0.45、选帧端却要求 0.65 导致补位再次被拒绝的问题。页面现显示实际处理 FPS。用户复测反馈不再丢手，同期约 30 秒、259 个处理帧均为 TRACKING；这只验证该段测试，不代表任意遮挡都能识别。

诊断接口 `http://127.0.0.1:8090/api/diagnostics/hybrid` 保留最近 600 个处理帧的两个模型类别、掌部是否入镜、各段耗时、选用来源及拒绝原因；不保存相机图像。需要再次排查时，应分别检查模型漏检、边缘拒绝、分类门槛和处理超时，不能仅凭页面的“丢手”提示判断。

四指侧摆：微张标定的负向变化映射到关节负向量程，修复无名指、小指增益被错误截成 0.2 的问题。加载旧配置时，用保存的并拢、微张样本重算增益。深度掌面先确定腕到中指根的前向轴，再正交化横向轴，与几何解算统一。MCP 从 35° 到 55° 弯曲时逐渐降低深度侧摆修正权重；达到 55° 后该指只保持侧摆，MCP/PIP 继续跟随，伸直后恢复侧摆。MediaPipe 临时补位屈伸时保留上一 WiLoR 侧摆，避免跨模型零位跳变。

**首次使用双源侧摆需快速归零一次**：刷新 8090，页面顶部“四指侧摆 · 快速归零”中，掌心朝前、四指并拢伸直，点击“采集四指并拢零位”，准备 1 秒、采样 7 秒，至少 20 个四指有效配对帧；完成后点击“应用侧摆零位并保存”。不重采拇指，不改变屈伸偏置、骨长和已有侧摆幅度比例。保存会备份旧配置；`side_sway_zero` 分别记录四指 WiLoR 和深度原始零位。深度观测先减自己的零位再加 WiLoR 零位，之后才混合和应用原有映射，避免将两个来源的绝对角直接混合后共同减一个偏置。没有配对零位时只沿用 WiLoR，不把未归零的深度侧摆混入。此处理不强行设定两指间距，也不保证任意姿态下的物理间隙。

**侧摆主值取三维，不取二维投影角**：本模式保留原有屈伸和拇指路径，只将四指侧摆主值改为 WiLoR 近节骨段在掌面坐标中的 `atan2(x,y)`。原 FrontHandEstimator 的二维侧摆约束在掌面转动或屈伸时会混入投影变化，不再用于本模式的最终侧摆主值。三维零位优先读取 `side_sway_model_zero`；旧配置可从已保存的并拢姿态 canonical 骨架还原，无需额外重采。深度权重最多 0.35，修正量最多 ±4°，分歧超过 25° 时保留三维主值。三维侧摆不可观测时保持上一目标，深度不会以 100% 权重重新接管。相邻手指的模型三维结果本身仍可能受遮挡影响，这些限制只约束解算与融合，不提供物理防碰撞保证。
