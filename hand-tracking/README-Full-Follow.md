# 全手摄像头跟随

扩展原食指模式，控制左手五指的 16 个独立目标，并按 URDF 生成 21 个关节目标。默认启动不使能，页面点击“开始全手跟随”才开始。普通食指模式仍可单独启动。

当前工作区一键入口默认使用方案 B（WiLoR）。实机直接使用 B 推理，不同时运行 A 的对照计算，加载独立 `profiles/wilor-current.json`。GPU 推理进程由独立 uv Python 3.10 环境提供，摄像头/SDK 转发仍在 uv Python 3.11 中运行。切换识别后端需重启当前会话，不能在已使能时通过下拉框切换。

```powershell
& D:\Dev\wslc\Start-HandFollow.ps1 -Tracker wilor
& D:\Dev\wslc\Stop-HandFollow.ps1
# 回退到 A，重启后仍需手动开始
& D:\Dev\wslc\Start-HandFollow.ps1 -Tracker mediapipe -Restart
```

打开 <http://127.0.0.1:8090/>，恢复识别、完整展示左手，再点击开始。页面“暂停并失能”停止全手；停止不自动回零，失能后姿态可能自然变化。整手模型仍为预览目标，表格“控制指令”才是实际桥接进程正在使用的目标。

当前 D435 + WiLoR 链路使用以下入口，保留三姿态标定及已保存的双源侧摆零位：

```powershell
& D:\Dev\wslc\Start-HandFollow.ps1 -Tracker wilor-d435 -Restart
& D:\Dev\wslc\Stop-HandFollow.ps1
```

该入口复用现有 wslc SDK 容器，自动启动独立 WiLoR 后端；不安装 WSL 或新镜像。启动时连接左手并读取反馈，五指保持失能；页面恢复识别后手动点击“开始全手跟随”。首次连接失败时检查有线 IPv4：电脑 `192.168.0.1/24`、左手 `192.168.0.102`。仅有 `169.254.*` 地址时，在管理员 PowerShell 运行根目录 `Set-HandNetwork.ps1`；该脚本校验指定 Realtek 有线网卡并备份旧配置，不添加网关或 DNS，不修改 Wi-Fi。

页面同时显示 RGB 识别画面、对齐 RGB 的 D435 深度伪彩画面和机械手模型；宽屏并排、窄屏换行。深度与 RGB 复用同一源帧并保持同一镜像方向，黑色表示无有效深度，颜色范围标在画面下方（默认 0.20–1.50 米）。切换后台或停止网页服务会释放两路网页视频请求，不额外打开相机。

## 速度、范围和运行时间

- 全手模式使用 SDK 原有速度、加速度参数，不再写入 20°/s、60°/s²，也不再逐关节限制目标变化速度。发送端直接使用最新滤波目标；食指试验模式仍保留原有限速。
- 四指使用共同的自适应滤波系数；拇指使用独立系数，避免四指运动使拇指抖动被直接放行。取消识别映射的 90°/s、360°/s² 速度/加速度限制。四指侧摆超过 12° 的突跳需连续两帧确认；大幅弯曲时保持难以观测的侧摆值。滤波不等于无延迟，也不能恢复摄像头看不到的信息。
- 拇指骨段目标与标定对指目标在逆解前先经过三帧因果中值处理，抑制单帧尖峰，再按时间平滑（时间常数静止约 240 ms、连贯运动约 40 ms）。最近四次位移的方向一致性与速度共同决定快速响应，避免把随机噪声当作主动运动；静止时增加 1.2 mm 任务空间死区。逆解加强静止连续性，远处的备选解只有明显改善拟合时才替换。输出独立自适应平滑（100–25 ms）并设置 0.4° 微小变化死区；这不是新增速度上限。恢复识别、切换或应用标定会清空输入滤波历史，超过 250 ms 的观测间隔重新初始化。中值处理通常增加一帧延迟，低速动作更平滑但可能略有拖延；单目深度的缓慢漂移仍可能传到输出。
- 四指侧摆取模型交集与 ±25° 的交集，屈伸取模型交集与 0–65° 的交集。全手不再使用食指试验的 0–10° 缩放。
- 拇指四个独立关节按 SDK 配套 URDF 与预览 URDF 的上下限交集限制，并向内预留 2° 边界余量。例如根部外展 j0 的发送范围约 2–78°。IP/MCP 先取共同允许范围，保持 1:1 联动。
- 另结合设备实际 SDK 日志：拇指 j1 的上限为 0.53 rad，预留 2° 后软件上限约 0.4951 rad（28.4°）。覆盖配置在 `hardware/device-limits.json`，启动时校验 SDK 1.4.7 / 固件 3.2.8；版本不符不进入使能。该日志覆盖不是完整硬件限位标定，SDK 错误处理仍保留。逆解、预览滤波与发送端使用同一限位，避免只在发送末端截断。
- 四指 DIP/PIP、拇指 IP/MCP 仍依模型 1:1 联动，不宣称独立控制 DIP/IP。
- **没有固定运行时长上限**，全手模式取消 30 秒自动结束。仍需有效识别、页面心跳、新鲜设备反馈和无故障状态；丢手/超时/异常会失能，不会自动重新开始。

此处“放开速度”指撤除本程序额外速度限制，保留 SDK 自身参数和错误处理；没有把 SDK 参数设置为任意极大值。关节限位不保证所有组合均无自碰撞；按用户要求，本次不增加复杂碰撞求解。

## 识别与停止

人手连续关键点与对应后端个人标定继续生效。开始时必须有有效拇指和四指屈伸数据；运行中拇指拟合暂时无效时保持已有拇指姿态，四指继续更新。运行中单指屈伸短暂无效可保持原目标至 500 ms，其余可靠手指继续，连续无效超过 500 ms 才停止；全手丢失仍按原有有效性机制停止。大幅弯曲导致侧摆不可观测时允许保持侧摆。仅显示 Left 并不足以开始。

B 与 A 统一使用小于 200 ms 的有效目标标准，避免 B 结果虽有效却被旧的 150 ms 发送条件拒绝；原生 250 ms 目标/反馈、600 ms 页面心跳不变。WiLoR HTTP 推理失败的帧明确无效，适配器断开异常连接、下一帧重建；不会继续发送旧目标冒充新识别，不自动重新使能。

`wilor-d435` 单独使用 400 ms 的真实采集年龄上限，以匹配同帧两模型约 8–9 FPS 的处理间隔；进入映射的新识别帧自身仍须在采集后 200 ms 内完成。实机模式不会采用预览补帧的新时间戳，漏检或超时只保持已有目标，真实采集年龄持续增长，到期停止并失能。相机恢复只恢复页面识别，不重新使能机械手。其余后端仍保持原有 200 ms 标准；原生 250 ms 命令/反馈保护及 600 ms 页面心跳不变。

SDK 1.4.7 的错误码 3 为 `ERROR_CODE_OUT_OF_RANGE`，并不指出哪一关节。本程序首先对发送目标限幅。若已运行并存在 SDK 接受过的目标，而新的全手目标被以错误码 3 拒绝，则只进行一次重发：保持上一组已接受的五个拇指关节值，仍使用新的四指目标。成功则保持全手跟随，并提示“拇指目标被 SDK 限制”；后续拇指目标重新可用时自动继续更新拇指，不重新使能。若重发仍被拒绝、首次目标即被拒绝、通信异常或硬件故障，则保留全手停止处理。该处理不推断所有错误码 3 都来自拇指，不搜索极限姿态，不清除硬件故障。

Windows 页面心跳每 200 ms 更新，过期 600 ms 停止转发；Linux 原生进程独立检查 250 ms 目标/反馈超时。切换后台页面会请求停止，页面关闭或网络/进程异常也会触发超时。重新开始需要手动点击。取消固定运行时限没有取消这些数据有效性检查。

SDK 模型、预览模型的关节限位与联动域在启动时重新计算，保存到 `profiles/full-hand-limits.json`（Git 忽略）。原生进程独立验证 21 个输入、有限值、目标限位和联动关系。全手模式不再把失能后的实际反馈位置与摄像头目标范围作比较：实测食指 PIP 失能后约 −8.2°，原先“目标范围 ±3°”检查会拒绝启动。实际关节范围交由 SDK 模型处理；故障、使能状态异常、目标/反馈过期仍请求五指失能，失能未确认时不自动恢复。

“控制指令”只显示已发送的目标；本进程尚未发送运动命令时显示 `—`，不再把初始缓存的全零数组显示成实际控制指令。启动未成功会退出请求状态并显示原因，不自动重试使能。

本模式共用已有 wslc 镜像和专用 SDK 容器，不安装普通 WSL，不启动 Explorer/ROS 后端。Windows Python 继续使用 uv。进程退出时先请求失能，再恢复原 SDK 速度/加速度参数；SDK Disconnect 也可能全指失能。不得与其他控制器共用设备连接。

## 重启后帧率异常的排查记录（2026-10-21）

WiLoR + D435 的相机采集约 30 FPS，识别处理正常约 8–9 FPS，两者不是同一指标。本次重启后，有手时整帧处理曾超过 200 ms，导致有效目标不足；不是相机采集降到了 4–5 FPS。

启动脚本现固定 OpenBLAS、MKL、NumExpr 为 1 个线程，OMP 为 2 个线程；主服务和 WiLoR 后端的 OpenCV 为 1 个线程，后端 PyTorch 为 2 个线程，减少多个视觉库同时开线程的竞争。混合链路关闭 D435 采集线程中重复的双画面编码，网页 RGB 和深度画面仍由主服务生成。识别算法、个人标定和目标有效期保持原设置。

清理动态壁纸、PowerToys 后重新启动主服务与 WiLoR，有手采样 82 帧：MediaPipe 平均约 12 ms，WiLoR 请求平均约 90 ms，整帧平均约 129 ms、最大约 167 ms，处理约 8 FPS；用户确认恢复可用。初始有手样本曾约 306 ms，全部超过 200 ms。线程限制改善了 MediaPipe 耗时；WiLoR 也在后端重启后恢复，但尚不能把骤降的具体触发原因归结为某一个后台程序。上述结果不代表相机或模型能达到 30 FPS。

随后用户完整重启，问题再次复现，说明上述线程和编码调整没有解决重启复发。进一步在同一组进程中做可逆对照：全部核心可用、Windows 自动调度时，整帧平均约 283 ms、约 4 FPS；仅主服务限定性能核仍约 222 ms；两个服务都限定性能核约 153 ms。恢复全部核心并显式禁用进程执行速度节流后，82 帧平均约 122 ms、约 8 FPS，无一超过 200 ms。撤销显式设置又回到约 265 ms、约 4–5 FPS，重新设置恢复。这把此次反复骤降定位到 Windows 自动执行速度节流，而非识别算法变化。

主服务和 WiLoR 现在启动时均调用工作区根目录 `vision_runtime.py`，用 `SetProcessInformation(ProcessPowerThrottling)` 显式设置执行速度位 `ControlMask=1, StateMask=0`。原来的 `ControlMask=0, StateMask=0` 表示由 Windows 自动决定，不能据此判断自动节流已关闭。新策略保留其他电源标志、不限制 CPU 亲和性、不提高进程优先级，也不修改整机电源方案。整理或复制工作区时请保留根目录的这个公共文件。

修复后连续进行了两轮根目录一键停止、启动，两轮主服务和后端均回读确认策略生效，CPU 仍全部可用、优先级仍为 Normal。第二轮用户实际跟随时采样 130 个单手帧：MediaPipe 平均约 11 ms，WiLoR 请求平均约 75 ms，整帧平均约 115 ms、最大约 144 ms，平均约 8.7 FPS，无超过 200 ms 的帧；实机反馈故障码为 0。158 项 Python 回归测试通过。分段数据见 `logs/low-fps-policy-restart2-20261021.json`，初始复发现场见 `logs/low-fps-recurrence-20261021.json`。

下次若再次突然变慢，先保存 `http://127.0.0.1:8090/api/diagnostics/hybrid` 和 `http://127.0.0.1:8093/health`，对比 `capture_fps`、`mediapipe_ms`、`wilor_ms`、`capture_age_ms`、`mapping_ms` 与 `processing_ms`。主服务 `/api/status` 和后端 `/health` 的 `runtime_power_policy` 应显示 `applied=true, control_mask=1, state_mask=0`；`/health` 还包含后端推理和检测器分段耗时。按现有一键停止、启动命令重启即可，不必重新标定；启动后仍须手动开始跟随。脚本不会自动关闭用户的其他软件。

## 通信诊断与连接复用

2026-10-18 排查发现，Windows 到本地桥 `127.0.0.1:8092` 的请求存在间歇超时和 Windows 10053/10054 错误；22:37:59、22:39:13 附近的本地桥超时与停止记录重合。同期没有对应的 SDK 设备断开记录。现场 12 次设备 ping 无丢包，另一次 400 次本地状态采样无错误、最大 RTT 约 27 ms。这能定位到本地桥请求层异常，但不能据此排除所有偶发的设备网络问题。

状态读取和控制发送现各自复用独立 HTTP 长连接，替代每次请求新建连接；服务端启用 HTTP/1.1、TCP_NODELAY 和更大的接入队列。闲置连接在下一次请求前重新建立。失败的控制请求不会自动重放，避免重复使能或发送过期目标。此次不放宽原生 250 ms 目标/反馈保护。

部署后失能状态下连续测试 60 秒：状态请求 1175 次、停止请求 1179 次，共 2354 次无错误；两条通道各复用一条连接，最大 RTT 均约 16 ms，最大设备反馈年龄约 79 ms，全程未使能。结果保存为 `logs/communication-check.json`。Windows 48 项、原生食指 7 项、全手 11 项回归检查通过。该检查验证本地请求与停止路径，不替代长时间实际运动下的复测。

本地桥异常不会再把界面重置为“只读模式 / 运动调用 0”，保留模式和计数，同时将反馈标为无效。SDK 设备断开、设备反馈过期、摄像头目标未送达、本地桥异常分别显示。Windows `logs/follow-events.jsonl` 记录开始、自动停止和手动停止前的原因；`logs/sdk-dry-run.jsonl` 会立即记录本地桥异常，而不只依赖每秒抽样。完整掉线时仍失能，恢复连接不自动使能。
